# 知识笔记规范（Obsidian）

`docs/Debian` 与 `docs/Dotfiles` 是本机可见的软链，指向 Obsidian 知识库 `~/Code/Obsidian/知识梳理/` 下的同名目录。它们记的是**个人使用技巧**，不是仓库文档；已写进 `.gitignore`（绝对路径软链不跨机器，别的 checkout 里不存在属正常）。

## 与仓库文档的分工

| | 仓库文档（`docs/*.md`） | Obsidian 笔记（`docs/Debian`、`docs/Dotfiles`） |
|---|---|---|
| 回答 | 仓库**怎么设计的、怎么改** | 软件**有什么不显然的地方** |
| 例子 | 主题渲染流程、conf.d 怎么组合、脚本约定 | fontconfig 被系统覆盖的处理顺序、中文 PDF 怎么配 |
| 变更时机 | 仓库结构变了 | 踩到坑、学到新用法 |

同一件事不两处写。笔记里不重复仓库的配置事实（"本仓库把 X 链接到 Y"），仓库文档里不写软件使用技巧。

坑要分家：由**本仓库配置**引起、任何 checkout 都能复现的，写 [troubleshooting/](troubleshooting/)；属于**个人环境或软件本身**的，写笔记。

## 收录判据：只写增量知识

一条信息值得写，当且仅当它**不是**模型已熟悉或一次 `man`/`--help` 就能得到的通用常识。具体地说，值得写的有四类：

1. **坑**：默认行为误导人、报错看不懂、配置互相覆盖。写清「现象 → 原因 → 解法」。
2. **社区实践**：官方文档没写但社区常用的做法，或与官方推荐不同的、更实用的替代。
3. **环境相关的事实**：具体的版本行为差异、硬编码路径、协议细节、硬件/内核参数取值。
4. **组合与顺序依赖**：多个软件配合时非显然的先后顺序或冲突。

不值得写、应删掉的：

- 软件简介、定位、「特性列表」——放 frontmatter 的 `description`/`url` 够了
- 安装命令（`apt install X`）与包名罗列
- 配置文件位置、选项清单、默认值表——配置选项由 `config/` 里实际配置承载，其余查官方文档
- 通用快捷键表、常用命令速查——问一句或用 `--help` 就有
- 教程式的「概览 / 安装部署 / 配置详解 / 使用技巧 / 参考资料」四段模板
- 大段搬运官方文档

判断标准一句话：**没有增量知识就不该有这篇笔记的正文**。空的笔记要么补上有价值的内容，要么删。

## 写法要求：要能读懂，不只是能查到

这些笔记是给**未来的自己和读它的人**看的，不是给模型查表用的。所以「只写增量」与「写清楚背景」两件事要同时成立：

- 每篇开头用一两句交代**它解决什么问题、什么场景下会用到**。不必写成软件简介，但要让人知道为什么会有这篇笔记。
- 术语、缩写首次出现时展开；报错信息和命令输出要给出原样，别只写「报错说找不到」——读者需要能对号入座。
- 写坑要写具体场景：做了什么操作 → 看到什么现象 → 为什么反直觉 → 怎么解。
- 不要因为求短而省略前提。一个结论如果离开背景读不懂，就要把背景写出来。

反例（够短但读不懂）：

```
## @import 路径规则
相对当前文件解析。
```

正例：

```
## `@import` 是相对当前 rasi 文件解析的，不是 CWD

把配置拆成多个文件时，被导入的写法是 `@import "colors"`（不带扩展名），
路径相对当前文件所在目录。这意味着从别处用 `rofi -config /path/to/config.rasi`
启动、或把 rasi 单独拷出去时，写错的相对路径不会因为启动目录不同而诡异地
碰对，而是直接找不到被导入的文件。
```

## 单篇结构

frontmatter：

```yaml
---
title: 软件名            # 可选，缺省用文件名
date: 2022-03-03 20:05:25      # 创建时间，保留原值不改
lastmod: 2026-08-14 15:07:14   # 由 Obsidian 自动维护，不要手动改
tags: [Desktop, Linux]         # 见下「标签词表」
description: 一句话说明这是什么、解决什么
url: https://github.com/...    # 上游主页或官方文档，没有就留空
status: deprecated             # 仅已弃用笔记，其余省略
---
```

## 章节骨架

每篇用二级标题分组，二级标题只从下面这五个里选，不要自造新名字；具体的知识点一律放三级标题下。

| 章节 | 必需 | 装什么 |
|---|---|---|
| `## 概述` | 是 | 这是什么、解决什么问题、什么场景下会用到；已弃用的在这里说明取代关系 |
| `## 插件` | 否 | 仅插件类软件（vim、tmux、zsh）：按标签自动汇总插件笔记的 dataview 表格 |
| `## 要点` | 是 | 不知道就会踩坑的行为与事实，每条一个 `###` |
| `## 技巧` | 否 | 知道了能省事的用法、社区实践、与其他工具的组合，每条一个 `###` |
| `## 相关` | 否 | 真正相关的同域笔记 |
| `## 参考` | 否 | 外部链接（官方文档、上游仓库、issue） |

「要点」与「技巧」的分界：要点是「不知道会错」，技巧是「知道了更方便」。拿不准放要点。只有一条知识也照样写，不要为了凑章节造空标题。

### 插件类软件的索引表

`vim`、`tmux`、`zsh` 这类「本体 + 一堆插件各自成篇」的软件，主体笔记要在 `## 概述` 之后加 `## 插件` 节，用 dataview 自动汇总，**已弃用的插件也列在表里**（靠 `status` 列区分，不要从表里删）：

```dataview
TABLE description AS "描述", choice(status = "deprecated", "已弃用", "在用") AS "状态", url AS "上游"
FROM #vim
WHERE file.name != "vim"
SORT file.name ASC
```

这要求插件笔记带上对应标签，所以插件笔记的 tags 固定为 `[<软件名>, Plugin]`（如 `[vim, Plugin]`、`[tmux, Plugin]`）——这是少数「tags 必填」的场合，供 dataview 抓取。主题类（`nord.md`）同理，靠 `Nord` 标签汇总 `nord-vim`、`nord-tmux`。

已弃用笔记豁免这套骨架：保留原文结构，只在 `## 概述`（或原「概览」改名）里补取代关系即可，历史存档不必重排。

骨架示例（只是骨架，不是内容模板）：

```markdown
## 概述

rofi 是「模糊筛选任意列表」的前端：应用启动、窗口切换、脚本菜单都由它渲染……

## 要点

### `modi` 与 `display-*` 是两回事

……

### 同一个 key 在多个 rasi 里出现时，后加载的生效

……

## 技巧

### 用脚本喂给 rofi 一个自定义菜单

……

## 相关

- [[desktop/polybar|polybar]]
```

代码块给可直接复制的片段，并说明它解决什么问题。合并、迁移、废弃过的做法也值得留一句，注明何时、被什么取代——检索旧配置时有用。

## 措辞：记知识，不记这台机器

笔记是给别人（以及几个月后的自己）用的知识库，不是这台机器的运行日志。同一条经验要写成别人也能用的形式：

| 不要写 | 应该写 |
|---|---|
| 本机的 monospace 字体是 Maple Mono | 把中文字体插进 monospace 列表时，需要 `binding="strong"`（原因见下） |
| 我这里的 dunstrc 用了 Adwaita symbolic 路径 | Debian 打包的 `adwaita-icon-theme` 缺 `16x16/status` 目录，改用 symbolic 路径可绕开报错 |
| 我的配置里 `use-damage = true` | `use-damage` 关掉会……；开着的代价是…… |

涉及具体取值时可以举例，但要说明这是**一种可用做法**及其适用条件。禁止「本机」「我这里」「我的配置」这类表述，改写为「实践中」「一个可行的做法是」。

末尾按需加两个区块（都不强制）：

```markdown
## 相关
- [[vim]] - 只列真正相关的同域笔记

## 参考
- [官方文档](https://...) - 外部链接放这里
```

## 目录与命名

按知识领域分目录，与 `config/` 的分布无关。两个顶层各管一块：

`Debian/`——系统与桌面：

| 目录 | 内容 |
|---|---|
| `guide/` | 系统级流程：安装、初始化这类跨软件操作 |
| `system/` | 系统服务：时间同步、自动更新 |
| `desktop/` | 桌面组件：窗口管理器、状态栏、通知、启动器、壁纸、GTK、打开方式 |
| `input/` | 输入法与字体 |
| `terminal/` | 终端模拟器 |
| `media/` | 播放器与媒体工具 |
| `tools/` | 其他常用工具与配色主题 |

`Dotfiles/`——工具与配置：

| 目录 | 内容 |
|---|---|
| `shell/` | zsh 与它的插件、提示符主题 |
| `editor/` | vim 与它的插件 |
| `tmux/` | tmux 与它的插件 |
| `cli/` | 命令行/TUI 工具 |
| `mail/` | 邮件、日历、联系人 |
| `dev/` | 开发工具链：git、dotbot、binup、herdr、pi、wakatime |
| 顶层 | 各自的索引页 `Debian.md`、`Dotfiles.md` |

主体笔记（`vim.md`、`zsh.md`、`tmux.md`）放在对应子目录内，与它的插件笔记并列。

文件名用软件正式名的小写形式（`ripgrep.md`、`offlineimap.md`），不加版本号与中文后缀；中文文件名只留给 `guide/` 的系统级指南。新增笔记时优先检查是否已有同类笔记可以并入。

目录内链接一律用**短链**（`[[ripgrep|ripgrep]]`），不要写 `[[cli/ripgrep]]`——文件名在全库唯一，短链在目录重整时不会断。

## 标签（可选）

tags 不是必填项，只在 dataview 或其他检索需要时才加——`editor/`、`tmux/`、`shell/` 下插件笔记的 `Plugin` 标签就是这么来的（`nord.md` 里的 dataview 靠 `#nord` 汇总同主题插件），不要为了分类而加。

需要加时复用既有词，不造新词：

- 平台：`Linux`、`Debian`
- 形态：`Desktop`、`CLI`、`TUI`、`GUI`
- 领域：`dotfiles`、`shell`、`editor`、`mail`、`输入法`、`中文`
- 插件笔记：`Plugin`（供 dataview 抓取）
- 索引：`MOC`（只给 `Debian.md`、`Dotfiles.md`）

已弃用不写进 tags，用 frontmatter 的 `status: deprecated`。现有笔记里无用的 tags 可以删。

## 索引页（MOC）

`Debian.md`、`Dotfiles.md` 是各自目录的唯一入口，结构固定为：

1. 一段说明这个目录收录什么
2. **在用**分区：按类别列出笔记，每条一句话（与笔记 `description` 一致）
3. **已弃用**分区：列出 `status: deprecated` 的笔记，注明替代品
4. **跨域关联**：与知识库其他目录（`NAS`、`Selfhost`、`开发工具`）真正相关的交叉点

索引里的链接用 `[[子目录/文件名|显示名]]` 或短链 `[[文件名]]`（Obsidian 按唯一文件名解析）。**新笔记必须加进索引**，弃用时从在用区移到已弃用区。

## 维护约定

- **同步是这两个软链存在的意义**：改动 dotfiles 时，若波及这两个目录涉及的软件或用法（换工具、改配置、踩到新坑），顺手更新对应笔记，别让笔记落后于版本。
- 卸载删除某软件后：笔记标注 `status: deprecated` + 「已被 X 取代」+ 迁移时间，正文保留，索引里移区。
- 笔记的改动不回写仓库（软链单向指向知识库）。笔记内容不进 git。
- 收件箱 `收件箱/已整理/` 里与本目录相关的条目，整理时并入对应笔记，不留重复。
