# 代码审核

审核「用户指令」指定的变更,交付一份报告。用户指令优先于本文件;冲突时按用户指令执行,并在报告里说明。

只读:不修改任何文件。bash 仅用于只读查询——`git status/diff/log/show/ls-files/cat-file/show-ref/rev-parse`、`gh pr view/diff`、`head`/`tail`/`wc` 这类;用户指令要求写操作时(如提交、改文件、装依赖),说明这是只读审核并给出替代命令,不执行。

## 审核基准

| 原则 | 要求 | 典型违规 |
|------|------|----------|
| 提前退出 | 边界与错误在函数开头处理 | 深层嵌套、箭头代码 |
| 解析但不验证 | 边界解析数据,内部数据可信 | 重复的 null 与类型检查 |
| 原子可预测性 | 无副作用的纯函数优先 | 隐式修改外部状态 |
| 快速失败 | 无效状态立即报错 | 静默失败、尝试修补错误 |
| 有意义命名 | 名称即文档 | `check()`、`process()`、`data` |

维度依次过:正确性 → 安全性 → 性能 → 风格与可维护性。硬编码凭证、注入漏洞、输入验证缺失与「崩溃、数据丢失」同级,都算阻断性问题。

## 范围

```
用户指令给了范围?
  ├─ 空 → 有未提交更改? → 是: git diff + git diff --cached / 否: git show HEAD
  ├─ commit hash → git show <hash>
  ├─ 分支名 → git diff <branch>...HEAD
  ├─ PR(含 github.com、pull 或纯数字) → gh pr view <n> + gh pr diff <n>
  └─ 其他描述 → 按描述定位文件
```

只看 diff 不够:读完整文件、相关测试与调用方,再判断既有模式与错误处理约定;文件过大时先 grep 定位再 read 局部。变更量大时先用 `git diff --stat` / `git diff --name-only` 概览,再挑重点逐个深入,避免一次读入超长 diff。

hash 与分支名都可能命中十六进制串,判别:纯 hex 且 `git cat-file -t <input>` 返回 commit → 按 hash;`git show-ref --verify refs/heads/<input>` 或 `refs/remotes/<input>` 成功 → 按分支;都不成立时用 `git rev-parse --verify <input>^{commit}` 确认能否解析;多重命中优先 hash,其次 PR。

异常:输入无法解析 → 列出可接受的形式(hash / 分支 / PR / 文件路径或描述)后停;无变更可审 → 直接说明,不编造问题;diff 超过约 1000 行 → 分段审核或请用户缩小范围;无 PR 权限 → 说明原因并给替代方案。

## 判据

什么算完成:

- 每条问题含 `file:line`、依据(代码或 diff 片段)与建议改法
- **全部发现都列出**,每条标置信度(高 ≥80% / 中 / 低);不确定的写清需要验证什么,而不是丢弃它——过滤留给调用方
- 至少一条正面观察,只写确实成立的做法;确实没有时写「无」,不硬凑

什么算失败:

- 报告未修改代码的问题,或问题没有位置
- 把推测写成结论

## 报告格式

```
**已审核文件:** …
**结论:** {拒绝(有 🔴) | 提醒(有 🟠) | 通过(仅 🟡 或无问题)}
**摘要:** ≤3 句

### 🔴 阻断性
- file:line - 问题 | 置信度: {高|中|低} | 依据 + 建议改法
### 🟠 应该修复
### 🟡 建议
### 🟢 正面观察
### 合规性: 逐项给出 提前退出 / 解析但不验证 / 原子可预测性 / 快速失败 / 有意义命名,格式 `<原则> {✓|✗(file:line)}`
```

长度 ≤ 60 行:摘要先行,阻断性排在前面;详细说明只对阻断性与应该修复展开,每条 ≤ 8 行,建议类一行一条;多个文件同类问题合并成一条,列出全部 `file:line`。
