# Prompt 优化

## 前提

- 目标是**指令遵循**:写进去的规则真的被执行。token 是副产品,不是目标。
- 最小充分集不等于字数最少(Anthropic: minimal ≠ short):该写的事实、契约、判据一条都不能省;要删的是冗余与脚手架。
- 本 skill 的规则都针对**产出物**(你正在写或改的那个 prompt),不约束审查者自己的思考步骤;用户点名本文件时,本文件就是产出物。

## 审计流程

1. 校准项目事实:核对真实存在的东西(测试框架、工具名、路径、命令),不提不存在的流程;引用的出处是可核验的断言——链接要可达,文档标题与正文要真的支撑它标的那件事;若被审 prompt 依赖容易被误读的项目状态(如 git 的索引与工作区混合态),在产出物里加一句环境说明。
2. 逐段归类:
   - 留下 事实与项目约定、工具与参数、输出契约、判据;删掉或合并 思维脚手架、重复、人格化(用「友好」「专业」代替行为描述)、强度性措辞(靠 `CRITICAL`、emoji 强调)。
   - 可复制性检查:模型会照抄的模板里不得出现具体取值。
   - no-op 检查:一句「模型默认就会做」的指令付了负载却什么都没说,修法是整句拿掉,不是打磨用词。
   - 层级检查:每条常驻规则是否只服务部分分支?是则推到 disclosed reference 后面,并在指针里把它锚住。
3. 四问自审:核心指令能否更一目了然;逻辑是否自洽;最挑剔的读者会在哪一步失败;有没有更好的结构封装。
4. 一处一改,改完做一次对比:改动前后各在一个新会话里用同一请求跑一次,记录 结论、分级是否符合映射、输出行数(这三个值只供自己判断,不写进交付);结论变化就要判断是否变好,两次记录不一致就是不稳定,退回第 2 步重新归类。指针的改动照样要比:同一批用户说法分别去打新旧两段措辞。起新会话用宿主的子代理工具(pi 里是 `subagent` 并设 `inherit_context: false`);起不了就跳过,并在交付里注明「未做稳定性对比」。
5. 发现具有通用性的例外条件时,在交付末尾单列「建议回写本 skill」条目交由用户决定,不自行编辑本文件。

## 第一原则

1. **事实与约定留下,思维脚手架删掉**:事实、项目约定、工具名与参数、输出契约留下;思维步骤、推理提示删掉。判法:删掉某句后,模型对目标与边界的理解不变,它就是脚手架。
2. **一条约束只出现一次**:重复与相互冲突的指引都诱发错误行为——含糊或冲突的规则会让模型提前停下并卡住,反复写「先问用户」会让它对安全操作也请示。唯一例外:超过一屏(约 40 行)的长 prompt,末尾可放一句短的长度或风格提醒。
3. **判据优于流程**:写「什么算完成、什么算失败」,而不是列十步过程。判据要同时满足两条:**可检查**(能分清 done 与 not-done;模糊判据会诱发提前收工,因为注意力滑向「已经做完了」)与**穷尽**(「每处调用都改完」比「给一份改动清单」更逼出实地工作量)。
4. **语气就事论事,并说明动机**:不用 `CRITICAL` / `MUST` 这类强调,也不让 emoji 或大写字母承载语义强度;官方对照:`CRITICAL: You MUST use this tool when...` → `Use this tool when...`。禁令要给理由,而且优先改写成正面目标:禁令会把被禁行为一并激活(「不要想大象」的结果就是满脑子大象,弱修饰语压不住强激活的概念),写「一行注释说清为什么」优于写「不要写长注释」。
5. **结构只在混排时用**:需要区分指令、上下文、示例、用户输入时才分节或加 XML 标签;单条规则不必包一层标签。
6. **输出模板只写字段与取值范围,不写具体取值**:模型会把模板里的字面值当成答案照抄。例:模板写 `结论: 通过`,报告就永远是「通过」;写 `置信度: 高`,每条问题都会填「高」;应写 `结论: {通过|提醒|拒绝}`。
7. **用已有的词当锚(leading word)**:一个预训练里已存在的紧凑概念(`tight`、`red`、`tracer bullet`)反复以 token 形式出现,能以最少 token 锚住一整片行为,并让「你的话、文档、代码里的同一个词」互相指向。自造词不招募任何先验,你要付的正是预训练词白送的定义成本。把反复展开的三词短语(「快、确定、开销低」→「顺手」)收成一个词。
8. **环境是事实的真源**:`package.json` 脚本、配置文件、目录结构、`--help` 输出这类一次查找就能拿到的,不要写进 prompt(它会过时);只缓存查不到的:没写下来的约定、选择背后的理由、配置不承认的坑。

## 指针与描述

`description`、AGENTS.md 里引一份文档的那一行、斜杠命令的提示语,都是**指针**:待在上下文里,命名一份没进上下文的东西,并编码「什么时候去取」。指针的**措辞**(而不是它指向的东西)决定触发率,所以穿过指针才能拿到的必备内容配一句写弱的指针,是**变异 bug**:先磨措辞,磨不动才考虑内联。

- **把锚词放最前**:指针就是锚词干活的地方,别把关键概念埋在从句尾部。
- **每个触发词对得上一句用户的原话**:说不出它接的是哪句话,它就是个装饰;用户常说而描述里没有对应的词,那条路径就是死的。
- **删掉正文已经承载的身份描述**:正文第一句说清了这是什么,指针里就别再说一遍。
- **常驻指针按词计费**:它每轮都在花,修剪门槛要高于正文。

## 放哪一层

每条内容都要选一层,按「模型多快需要它」排:

| 层 | 成本 | 适用 |
|----|------|------|
| 文件内的步骤 | 每轮常驻(context load) | 每次都要执行的顺序动作 |
| 文件内的参考 | 每轮常驻 | 每个分支都会查阅的定义、规则、判据 |
| 推出去的参考(disclosed reference) | 只付指针那一行 | 只有部分分支才需要的细节 |

判据:**每个分支都要的写在文件里,只有部分分支才到的推到指针后面**。推得太少,顶层臃肿(sprawl);推得太多,模型找不到真正需要的东西。同一概念的定义、规则、例外放在同一标题下(而不是散落各处),读一处能带出邻居。

两种负载:常驻材料花 **context load**(每轮的 token 与注意力);「有哪些文档、何时翻哪份」花 **cognitive load**(人是索引)。后者不是要最小化的成本——它买的是人类判断力,只花在判断真正重要的地方。

## 逐项决策

| 元素 | 推荐做法 | 例外 |
|------|----------|------|
| 角色声明 | 一句话,或直接描述职责 | 需要特定语气时写清「怎么写」,不要用「友好」「专业」这类标签 |
| 强制 CoT | 删 | 宿主关闭思考模式时(如把 pi 的 thinking 设为 off)可用「think thoroughly」+ `<thinking>`/`<answer>`;非推理模型仍可用 |
| few-shot | 输出格式是产品要求、或实测存在缺口时才用,包在 `<example>` 里 | 不堆边界用例;示例必须与指令一致 |
| 自检、双查指令 | 删 | 有具体验收标准时写成判据,不写「再确认一遍」 |
| 笼统指令(「只报严重问题」「拿不准就用 X」) | 删。全报,每条标分级与置信度,由调用方过滤 | 无 |
| 工具说明 | 只暴露该任务需要的工具;工具自身的 description 简短精确 | 无 |
| 优先级 | 显式声明「用户指令优先于本文件」 | 无 |
| 委派判据 | 写清什么情况委派、什么情况自己做;能设上限就设 | 无 |
| 分级与汇总结论 | 每级写清触发条件,并给出汇总映射(如:有阻断性问题 → 拒绝;只有建议 → 通过) | 无 |

## 目标骨架

一句话职责 → 判据(完成 / 失败 / 分级映射) → 不可推导的流程与命令 → 输出契约(格式 + 长度) → 边界(不做什么、冲突时听谁的)

## 预算(个人约定,非官方结论)

| 类型 | 目标 |
|------|------|
| agent 定义 | ≤ 80 行 |
| 斜杠命令模板 | ≤ 30 行 |
| SKILL.md | ≤ 120 行 |
| AGENTS.md 每条规则(一个 bullet) | ≤ 2 行 |

计行不计空行与围栏行。超预算先按审计流程归类,不要直接砍内容,尤其不要为凑行数删掉排版空行。

## 交付

给出改动清单(位置 + 原问题 + 改法);改动行数(新增 + 删除,未原样保留的旧行计入删除)超过被审 prompt 总行数一半时给改写后的完整文本,否则只给改动的章节并列出未改动章节;无改动时只回一句「无需改动」。不逐段解释,不做自评表。
