# 深度研究

目标不是收集信息,而是**构建可信结论**。

## 执行方式

问题在末尾的 `User:` 行(首词是 `quick` / `standard` / `deep` 时按该档位执行,并从问题里去掉该词;没有就是 `standard`)。若是你自己判断该用本 skill,问题即用户当前请求。

先看你当前可用的工具列表(有没有 `subagent`),再按「值不值得为上下文隔离付一次启动开销」决定:

**预计要抓多个页面、多轮检索就委派**(standard / deep 档基本都是这种):交给 `general-purpose`,你只负责把问题交出去、再把结果原样呈现。**规则不要粘进 prompt,让它自己 read** - 粘贴等于你输出一遍(贵)且永久留在主对话里:

    subagent({
      subagent_type: "general-purpose",
      description: "深度研究: <问题摘要>",
      inherit_context: false,
      prompt: "你是研究专家。先 read ~/.config/pi/skills/research/SKILL.md,只按其中「# 研究协议」以下的内容执行,忽略「执行方式」一节(那是给主 agent 的)。用户问题:<问题>。档位:<quick|standard|deep>。按规则完成检索、验证与报告,不要提问,最后输出 evidence/answer/next_steps 三段。",
    })

**quick 档且答案就在本机、一两次调用就能确认时,自己做也行**,不必为了形式而委派。

为什么用子 agent:**双向隔离**。抓来的页面正文留在它那边,主对话只留浓缩后的报告;同时它在干净上下文里独立判断,不带你的假设、已得结论和搜索轨迹。代价是它看不到本对话,所以规则与问题必须让它自己拿到(读文件,或写进 prompt)、提示词要自包含;`inherit_context: false` 是显式声明这点,别改成 `true`。prompt 里只给问题、档位和规则,不要塞你的中间结论或已经拉过的页面正文 - 那会把它带向你的思路。

拿到结果后原样呈现给用户(报告本身就是交付物),不要自己再复述一遍。若 spawn 失败或提示 agent 类型未知,改用下面的方式自己执行。

**没有 `subagent` 工具** → 你自己执行:严格按「# 研究协议」完成检索与验证,并输出同样的三段结构。

不要询问用户,一路做完。

# 研究协议

使命:**理解意图 → 规划子问题 → 并行检索 → 交叉验证 → 交付可复核的结论**。

## 1. 先规划,再动手

动手前输出「研究计划」小节(简短,别写成长文):

```
**研究计划**
假设: <用户字面问什么,深层想达成什么>
成功标准: <覆盖哪些子问题、关键结论要几个独立来源>
子问题:
  1. <标题> → 关键词: <宽口径短词> → 预期信源: <官方文档/论文/issue/…>
  2. ...
档位: <quick|standard|deep> → 预算 <N> 次工具调用 / <M> 轮
时效: <是否需要近期资料;需要就用 recencyFilter,别在关键词里塞年份>
风险: <可能搜不到什么,备用关键词或路径>
```

问题本身若涉及本仓库代码(「我们的实现是否符合规范」这类),子问题里要同时安排代码侧(读源码/配置)与外部侧(规范/官方文档)。

## 2. 档位预算(硬性)

| 档位 | 轮次 | 工具调用上限 | 覆盖要求 |
|------|------|-------------|---------|
| `quick` | 1 轮 | ≤5 次 | 1-2 个子问题;单源结论必须标注「来源唯一」 |
| `standard`(默认) | 2-3 轮 | ≤12 次 | 全部子问题;关键结论 ≥2 个独立来源 |
| `deep` | 3-4 轮 | ≤20 次 | 全部子问题 + 对立观点/失败模式/边界条件专项;关键结论 ≥2 独立来源,且至少 1 次 `source_check` |

预算表是**上限**不是目标,接近上限就停止检索、交付已有发现并写明缺口。

## 3. pi 的检索工具(与 opencode 不同,按此用)

| 工具 | 用法 |
|------|------|
| `web_search` | 发现入口。一轮一次传 2-4 个 `queries`(不同角度、不同措辞),工具并发最多 3 个。`recencyFilter: "month"/"year"` 管时效,`domainFilter: ["docs.x.com", "-forum"]` 管信源,`numResults: 10` 要广度。关键词**从宽到窄**:起步 5 词以内,命中多了再收窄。provider 一般不用指定(已配好路由链);要交叉验证同一结论时才用 `provider: "all"` 换引擎再问一次 |
| `fetch_content` | 读正文。一次传 `urls: [...]` 批量抓(2-3 个)。PDF 自动转 Markdown。**不要用 `mode: "answer"`**(本机不可用) |
| `source_check` | 关键结论的机械验证。传 `claim` + `queries`,可选 `fetchContent: true`;返回 `supported` / `contradicted` / `unclear` / `missing-evidence` + 精确 passage 引用 + 信源质量提示。**结论冲突时用它做裁决**,别靠印象 |
| `get_search_content` | 回查已抓正文,不重复抓取。用 `findText: ["关键词"]` 精确定位某个数字或原句,`urlIndex` 指定第几个 URL |

**GitHub 一律走 `gh`,不要用 `fetch_content`**:本机 `fetch_content` 抓 github.com / raw.githubusercontent.com 会被 SSRF 拦截(实测 `Blocked internal address`)。用 `gh search repos/code`、`gh api repos/<owner>/<repo>/readme`、`gh api repos/<o>/<r>/contents/<path>`、`gh pr view`、`gh issue view`。

本机 `web-search.json` 里 YouTube / 视频分析是关的,别指望读视频;PDF 与网页正常。

## 4. 检索节奏

- 一轮 = 一次「发现 + 深读」:`web_search` 拿到 URL → `fetch_content` 批量读高价值页面。**搜索与抓取是上下游,不要在同一批里混着发**。
- 与代码检索并行:代码侧(`read` / `grep` / `git log` / `gh`)和网络侧可以同时起步。
- 每轮结束输出一行缺口小结,再决定下一轮:

```
**[轮次 N/M]**: 已覆盖 X/Y 子问题。缺口:<具体缺什么>。下轮策略:<换关键词 / 换信源类型 / 换引擎>。
```

- 换轮次时换的是**角度或信源类型**(官方文档 → 源码 → issue → 论文 → 社区实测),不是把同一句话换个说法再搜一遍。

## 5. 证据规则

每条证据按此写:

```
<evidence>
- 来源 [1] https://… [一手/官方] [2026-03] 支撑句: "<从页面取的原句或紧贴原意的短句>" (✓ 与来源 [3] 一致)
- 来源 [2] https://… [二手/社区] [无日期] 说明… (⚠ 与来源 [1] 冲突:可能因版本差异)
- 来源 [3] /abs/path/file.ts:45 [代码验证] 本地实现,与来源 [1] 规范第 3 节不一致
</evidence>
```

- **编号按出现顺序(1-based)**,`<answer>` 里用 `来源 [N]` 引用。
- **引用要绑定到句子**:标了引用就必须真有那句话/那一段支持它。禁止「引了但页面上没这说法」——不确定就用 `get_search_content` 的 `findText` 回到原文核对;核对不到就不写这条结论。
- **独立性判定(转载不算共识)**:同一篇稿件被十家媒体转载、同一作者的系列文章、企业博客互相复述同一份发布,都只算**一个**来源。不同域名不等于独立来源,要看原始出处。
- **信源分级**:一手(官方文档/规范原文/源码/issue/论文/官方公告) > 二手(技术媒体、个人博客解读) > 聚合(内容农场、SEO 转述)。优先一手;能追到原始出处就追。
- **低质信号**(命中就降置信度或弃用):无署名、转述而非原始出处、营销或 spin 语言、对未来用推测语气、无日期、cherry-picked 数据、伪权威口吻。
- **时效**:网络来源尽量标发布日期;快速变化的领域(框架版本、API、定价)只采近期资料并说明截断点。
- **冲突**:能裁决就用 `source_check` + 时效/信源质量裁决;不能裁决就**并列双方**并注明各自来源、日期、可信度,不要偷偷挑一个。
- **区分来源类型**:`[代码验证]`(本仓库/源码实测,优先)与 `[网络来源]`(外部资料)必须标出来,别混着说。

## 6. 终止条件(满足任一即停)

- 所有子问题已覆盖,且关键结论达到本档位的独立来源要求
- 连续一轮无实质新发现(递减回报)
- 预算(轮次或调用数)用尽 —— 此时交付已有发现,**明确写出缺口**,不要为了凑满而续搜

## 7. 输出

```
<evidence>
…(见上)
</evidence>

<answer>

## 结论
<1-3 句直答,给判断与建议,引用 来源 [N]>

## 核心发现
### <主题>
<论证,关键声明带 来源 [N]>

## 不确定项
- <事项>:<不确定性原因 / 分歧双方与各自可信度>
- <事项>:<信息缺失>

</answer>

<next_steps>
- <用户可直接执行的下一步:命令、要读的文件路径、要落的改动>
- 剩余缺口:<还有什么没查到>
</next_steps>
```

## 8. 硬约束与自检

**硬约束**:只读,不创建/修改/删除任何文件;空结果必报(没找到就说没找到 + 可能原因 + 替代检索方向,绝不编造);引用本地实现给 `文件:行号`;每次工具调用都要能说清为了补哪个缺口。

**交付前自检**:
- [ ] 计划里的子问题都有证据,或注明未覆盖原因
- [ ] 每条关键结论的引用真能支撑它(不是「页面提到过相关词」);独立来源数达标,单源已标注,转载没被当成多个来源
- [ ] 冲突与不确定性已写出,没有被抹平
- [ ] 时效敏感话题标了日期;`[代码验证]` 与 `[网络来源]` 已区分
